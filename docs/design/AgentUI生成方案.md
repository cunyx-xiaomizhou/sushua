# Agent UI 生成方案

> 本文档为方案设计稿，用于对齐讨论和逐步校准。最终确认后作为实现依据。

---

## 一、问题背景

当前 UI 生成流程存在的核心问题：

1. **代码树示例导致 LLM 过度模仿**：注入的骨架/组件代码树被当作模板照搬，遇到不同场景不会变通
2. **注入上下文过多（560行），有效信息密度低**：核心布局原则（容器优先、分组封装）被淹没在细节中
3. **多阶段串行导致意图衰减**：Phase 2 骨架和 Phase 5 实现之间隔了两个纯文字阶段，结构意图丢失
4. **缺乏持久化状态**：跨轮对话依赖上下文记忆，换模型/上下文溢出时无法继续

## 二、整体流程设计

### 2.1 两轮制

| 轮次 | 目标 | 产出 |
|------|------|------|
| 第一轮 | 界面识别 + 容器形态 + 内容布局 + 骨架实现 + 任务分配 | 骨架 JSON（已执行）+ 任务清单 + 结构摘要 |
| 第二轮 | 逐区块填充实现（循环 N 次） | 各区块完整控件 JSON |

### 2.2 第一轮详细流程

**输入**：用户提供的策划案/需求文档

**步骤（三个独立决策 + 执行动作）**：

1. **识别界面** → 从策划案中提取独立的交互层/面板数量
2. **确定容器形态** → 每个界面属于哪种容器形态（见 §2.4）
3. **确定内容布局** → 每个界面内部的区块排列方式（见 §2.5）
4. **划分一级区块** → 沿主结构方向划分（不限数量，见 §2.7 区块定义）
5. **输出骨架 JSON 并执行** → 只有一级容器 Panel，带初始尺寸估算（可后续调整）
6. **功能点→区块映射** → LLM 自动将策划案功能点分组写入任务清单
7. **生成结构摘要** → 记录每个区块的 ID、尺寸约束、状态

### 2.7 区块定义与划分规则

**区块定义**：满足以下全部条件的界面子区域——
- 有明确的空间边界（与其他区块之间有间距或视觉分隔）
- 内部元素服务于同一个用户任务/同一组信息
- 可以被独立实现而不依赖其他区块的内部结构细节

**划分规则（关键）**：一级区块只在一个布局维度上划分，不混合正交方向。

正确示例（合成系统，全屏+左右分栏）：
```
一级区块（沿垂直方向划分）：
  - 顶栏（横向全宽，固定高度）
  - 内容区（横向全宽，填满剩余高度）

内容区的内部结构（左右分栏）在"区块细化"阶段处理，不在一级划分时做。
```

错误示例：
```
❌ 一级区块混合了上下和左右：顶栏 / 左侧列表 / 右侧详情
   → 顶栏是横向全宽，左右是纵向分栏，混在同级会导致拉伸时布局崩坏
```

**骨架尺寸策略**：骨架 JSON 中的 anchor/offsets 为初始估算值，非最终确定。第二轮填充时如发现不够用，可通过 update 指令动态调整容器尺寸。

### 2.4 容器形态（第一层分类）

描述界面本身如何放置在屏幕上：

| 容器形态 | 说明 |
|----------|------|
| 全屏覆盖 | 占满整个屏幕，是最常见的主界面形态 |
| 居中弹窗 | 屏幕中央固定尺寸面板，通常有遮罩层 |
| 边缘面板 | 从屏幕某侧（左/右/上/下）延伸出的面板，可为任意比例，覆盖在主界面之上 |

### 2.5 内容布局（第二层分类）

描述界面内部区块的排列方式：

| 内容布局 | 适用场景 |
|----------|----------|
| 左右分栏 | 列表+详情（背包、合成、商店） |
| 左中右三栏 | 三栏信息（装配、对比） |
| 上下分段 | 信息+操作（结算、弹窗内容） |
| 上中下三段 | 标题+内容+操作栏 |
| 环状/径向布局 | 快捷菜单、技能轮盘、FPS快捷消息（元素围绕中心点排列） |
| 卡片流/瀑布流 | 成就墙、相册浏览、不规则尺寸内容列表 |
| 层叠/堆栈式 | 卡牌扇形展开、抽奖转盘、可翻页堆叠 |
| 节点图/自由画布 | 天赋树、科技树、节点自由分布+连线 |

> **注**：容器形态和内容布局是父子关系。容器形态决定界面"在哪/多大"，内容布局决定界面内部"怎么排"。例如：全屏覆盖+左右分栏、居中弹窗+上下分段、边缘面板(右)+上下分段。
>
> **后续调整预留**：当前保留完整布局列表注入。实验阶段如发现列表示例导致模型过度依赖/限制创造性，再考虑改为仅输出格式引导、不预置选项。

### 2.6 设计风险预警

> ⚠️ **LLM 设计经验依赖**：步骤 1-3 的决策依赖 LLM 预训练中的"游戏UI设计经验"。对于经典 UI 范式（列表+详情、Tab切换等），当前模型（Claude Opus 4.6）可以胜任。但对于非标准布局（复杂仪表盘、实时数据可视化等），可能需要外部知识库补充判断依据。后续如果实验发现模型在此步骤决策质量不稳定，再考虑引入向量知识库做范式匹配辅助。当前阶段不预置规则，避免 prompt 干扰模型自身判断力。

### 2.3 第二轮详细流程

第二轮分为两个阶段：**区块细化（结构设计）** → **控件填充（实现）**。

#### 阶段 A：区块细化（递归，子Agent并行）

主Agent将一级区块分发给多个子Agent并行处理。每个子Agent对自己负责的区块执行递归细分：

```
递归细分流程（对每个区块循环执行）：

输入：当前区块 + 该区块的功能需求列表

1. 判断：区块内需要放置的内容是否可直接原子化为叶子控件？
   ├─ 是（1-2个叶子控件即可满足）→ 标记"待填充"，结束细分
   └─ 否 → 继续：

2. 决定内部分几块、怎么分（上下/左右/HBox/VBox/其他）
   - 参考父区块语义角色和设计意图上下文
3. 创建子区块容器
4. 将功能需求分配到各子区块
5. 对每个子区块递归执行本流程（回到步骤1）
```

**终止条件**：区块内内容可直接原子化为叶子控件时，结束该分支的细分。

**每次递归只做一层**——不是一口气细分到底。

**子Agent 输入**：
- 本区块的尺寸约束（宽高范围）
- 本区块的子任务清单（从总任务清单摘出的对应条目）
- 布局决策规则（prompt 注入）

**子Agent 边界**：
- ✅ 可做：在本区块内部创建子容器、决定内部结构
- ❌ 不可做：修改本区块的外部位置/anchor、修改其他区块
- ⚠️ 可报告：发现父容器尺寸不够用 → 写入报告，由主Agent后续调整

**产出方式**：子Agent产出写入各自的文档文件（非直接执行 JSON），全部完成后由编辑器统一冷装载。

#### 阶段 B：控件填充（逐区块实现）

区块细化完成后，对每个已标记"待填充"的末端区块执行控件填充：

```
1. 读取该区块的子任务清单 → 确认需要什么控件
2. 原子化设计 → 确定具体控件类型和属性
3. 预检查（可选，开关控制）→ 调用布局计算器检查尺寸是否溢出
   ├─ 通过 → 步骤 4
   └─ 冲突 → 调整设计或报告需要扩容父区块
4. 输出创建 JSON → 写入文档
5. 标记任务完成
```

#### 冷装载机制

子Agent并行产出全部写入文档文件，不直接执行。编辑器提供"批量装载 JSON"能力：
- 按区块在骨架中的层级顺序逐个加载（父容器先于子控件）
- 区块之间无父子依赖，可任意顺序

### 2.8 布局计算器工具（编辑器提供）

编辑器为 Agent 提供一个辅助计算 API（非强制使用）：

```
输入：一组嵌套的 anchor/offsets 定义 + 父容器实际像素尺寸
输出：每个控件的实际渲染位置和尺寸（绝对像素）+ 溢出/重叠检测结果
```

用途：Agent在布局时如不确定多层嵌套后的实际像素效果，可调用此工具做精确判断。属于辅助决策工具，不强制要求每次都调用。

## 三、持久化文件设计

### 3.1 任务清单

**路径**：待定（GameScript 下某个位置）

**格式**：

```markdown
# [界面名] - UI实现任务

## 区块: [区块名] (id: xxx) [状态: 未开始/进行中/已完成]
- 控件组1描述
- 控件组2描述
- ...

## 区块: [区块名] (id: xxx) [状态]
- ...
```

**写入时机**：第一轮骨架完成后，LLM 自动生成

**读取时机**：第二轮每轮开始时

### 3.2 结构摘要（主Agent持有）

**用途**：主Agent用来追踪整体进度 + 多个子Agent产出后做最终整合检查。**不下发给子Agent**（子Agent只需知道自己区块的尺寸约束）。

**路径**：待定

**格式**：

```markdown
# [界面名] - 结构摘要

## [一级区块名] (id: xxx)
- 尺寸约束: 宽度~Xpx，高度~Ypx（可调整）
- 状态: 未细化/细化中/已完成
- 子区块:
  - [子区块名] (id: xxx) - 状态
  - ...
```

**写入时机**：第一轮骨架完成后首次生成

**更新时机**：区块细化完成后 / 控件填充完成后更新

### 3.3 子Agent任务文档（每区块独立）

每个子Agent拥有独立的任务文档，包含：
- 本区块尺寸约束
- 本区块功能需求列表（从总任务清单摘出）
- 细化过程记录（每次递归的决策和结果）
- 最终产出的 JSON（待冷装载）

## 四、Prompt 注入架构

### 4.1 永久注入层（≤80行）

始终注入到 LLM 上下文中的内容：

1. **意图路由**（~5行）：判断用户意图类型
2. **布局决策规则**（~20条）：条件触发式，非绝对铁律
3. **预检查清单模板**（~10行）：带开关
4. **ui-command 格式说明**：仅演示 JSON 格式，不含布局语义
5. **知识块路由表**（~15行）：关键词→知识块映射

### 4.2 每轮动态注入（从文件读取）

- 任务清单中当前区块的条目（5-15行）
- 结构摘要全文（20-40行）

### 4.3 按需加载层（知识块）

LLM 根据路由表自主判断需要哪些知识块：

- 组件模式参考（按钮/卡片/Tab/列表等，每块 150-300 字）
- 锚点速查表
- 样式属性参考

## 五、布局决策规则（纯文本，条件触发式）

> 以下为初版，需要校准和补充。

### 容器选型

- 当多个元素满足：同方向排列 + 等间距 + 无重叠 → 使用 HorizontalBox/VerticalBox
- 当元素为网格排列（行列规律） → 使用 GridBox
- 当内容可能超出可视区域 → 外层包 ScrollBox
- 元素位置各不相同/需要精确控制 → Panel + 锚点定位

### 分组封装

- 同侧 + 逻辑相关 + 视觉紧邻的多个元素 → 建父容器封装
- 仅位置相近但功能独立的元素 → 不需要额外封装

### 定位策略

- 需要跟随父容器自动缩放 → 拉伸锚点
- 固定尺寸且位置相对某边/某角 → 点锚点
- 流式容器内的子元素 → 不需要手动设置锚点
- 环形/径向排列的元素 → 居中锚点 + 角度计算偏移

### 间距

- 流式容器内 → 用 spacing
- 非流式容器内相邻元素 → 用 offset 计算

## 六、预检查机制

### 6.1 检查项（初版）

```
□ 尺寸冲突：当前控件组总尺寸是否超出父区块剩余空间？
□ 锚点重叠：是否与同级已有控件的定位范围冲突？
□ ID 唯一性：新控件 ID 是否与已有 ID 重名？
□ 容器选型：是否有应该用流式容器但没用的情况？
□ 耦合影响：修改是否影响相邻区块的位置/尺寸？
```

### 6.2 冲突处理

发现冲突时：
1. 先输出修正 JSON（update/replace）调整已有控件
2. 再输出本区块的创建 JSON

### 6.3 开关控制

预检查可通过配置开关启用/禁用，方便对比效果和迭代优化。

## 七、关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 示例代码树 | 完全移除 | 消除 in-context 模仿引力 |
| 规则表述方式 | 条件触发式 | 有反例时不自相矛盾 |
| 预检依据 | 落盘的结构摘要文件 | 不依赖对话历史，可换模型 |
| 任务追踪 | 落盘的任务清单 | 持久化，跨轮可读 |
| 自检机制 | 开关控制 | 方便迭代优化 |
| 实现粒度 | 每轮一个大区块 | 平衡效率和质量 |
| 美术资产 | 原子化阶段同步处理 | 不割裂结构和视觉 |
| 知识库 | 初期关键词路由 | 轻量，无额外依赖 |

## 八、待确认事项

1. 任务清单和结构摘要的具体存放路径
2. 结构摘要由 LLM 更新还是编辑器执行 JSON 后自动生成
3. 预检查的具体检查项是否需要增减
4. 知识块的拆分粒度和路由表具体内容
5. 布局决策规则是否完整，需要补充哪些
6. 美术资产填充的具体策略（留空/搜索/固定配色方案）
7. 第一轮骨架的"区块划分"颗粒度标准
8. 多界面项目时，第二轮的界面切换如何处理

### 已确认项

- ✅ 版型分类改为两层：容器形态（全屏/居中弹窗/边缘面板）+ 内容布局（完整列表）
- ✅ 第一步拆为三个独立决策：识别界面 + 确定容器形态 + 确定内容布局
- ✅ 不预置"界面数量判定规则"和"版型判断依据"，先依赖模型自身能力，实验后按结果决定是否补充
- ✅ 设计经验不足的兜底方案：外部向量知识库 + 路由索引（预留，当前不实现）
- ✅ 内容布局保留完整列表注入（模型对详细列举类内容仍有困难），后续实验后视情况决定是否精简
- ✅ 不确定时允许 LLM 主动向用户提问确认（如无法判定是独立界面还是主界面内控件）
- ✅ 当前定位：探索性研发，人在回路审核，先跑通流程再追求无人值守
- ✅ 一级区块划分不限数量，只在一个布局维度上划分（不混合正交方向）
- ✅ 骨架颗粒度：极简一级区块（方案A），内部结构由"区块细化"步骤处理
- ✅ 区块细化为递归流程：每次只分一层，终止条件=内容可直接原子化为叶子控件
- ✅ 子Agent并行细化各区块，产出写入文档，编辑器统一冷装载
- ✅ 子Agent输入：本区块尺寸 + 本区块子任务清单 + 布局规则（不需全局结构摘要）
- ✅ 全局结构摘要仅主Agent持有（追踪进度+最终整合检查）
- ✅ 骨架尺寸为初始估算值，填充时可动态调整
- ✅ 新增布局计算器工具：编辑器提供辅助API，Agent可选调用，非强制
